# OSF — Example Files

This directory contains real and synthetic OSF files used to learn the
format and to verify reader correctness across all language
implementations. There are two kinds of files: **generated reference
files** (synthetic, one feature per file) and **field samples** (real
recordings from optiMEAS measurement devices).

## `generated/` — synthetic reference files

Produced by the Delphi reference implementation (regenerate with the
headless `OSFGeneratorCLI`, see the repo `CLAUDE.md`). Each file targets
one feature so a correct reader can be validated piece by piece — for
every feature there is an OSF4 (XML-header) and an OSF5 (JSON-header)
variant.

| File (OSF4 / OSF5) | Demonstrates |
|---|---|
| `osf4_equidistant.osf` / `osf5_equidistant.osf` | Equidistant (fixed-rate) channel |
| `osf4_scalar_numeric.osf` / `osf5_scalar_numeric.osf` | Time-stamped floating-point scalar channels |
| `osf4_scalar_int64.osf` / `osf5_scalar_int64.osf` | Signed 64-bit integer scalar channel |
| `osf4_scalar_unsigned.osf` / `osf5_scalar_unsigned.osf` | Unsigned integer scalar channels |
| `osf4_gpslocation.osf` / `osf5_gpslocation.osf` | GPS-location channel |
| `osf4_timestamped_string.osf` / `osf5_timestamped_string.osf` | Time-stamped `string` payloads |
| `osf4_timestamped_binary.osf` / `osf5_timestamped_binary.osf` | Time-stamped `binary` blob payloads |
| `osf4_mixed.osf` / `osf5_mixed.osf` | Several channel types in one file |
| — / `osf5_mixed_extended.osf` | Extended mixed-channel OSF5 file |
| `osf4_message_event_string.osf` / `osf4_message_event_string_equivalent.osf` | The **same** `string` channel content twice: once as `bcMessageEvent` (control byte 4 — the deployed-firmware OSF4 encoding), once as `bcAbsTimeStampData`. Both files must decode channel-for-channel identically (DECISIONS §26). Two OSF4 files, not an OSF4/OSF5 pair; generated by `cargo run --example gen_message_event_refs` from `implementations/rust/osf-core/`. |

19 files in total (10 OSF4 + 9 OSF5) directly under `generated/`. A correct
reader must parse all of them without error. These files are the
cross-implementation read fixtures; the OSF4/OSF5 pairing also exercises
the version-deterministic rules (e.g. the `string`/`binary` null-terminator
handling).

Two sub-directories extend this set beyond the flat file list above. Both
are reached only through `examples/reference_manifest.json` — the
directory-scanning harnesses that glob `generated/*.osf` **non-recursively**
never see them:

| Directory | Contents |
|---|---|
| `integrity/` | OSF5 files at integrity profile level `crc`; a CRC-unaware reader would misparse them. See `generated/integrity/README.md`. |
| `malformed/` | Deliberately **non-conforming** OSF files (e.g. a zero-length data block). These do *not* fall under "a correct reader must parse all of them without error" above — the opposite: a correct reader must detect and skip the anomaly while still recovering the surrounding valid data. See `generated/malformed/README.md`. |

### `bcMessageEvent` writer audit — can anything here emit control byte 4?

**No.** Audited 2026-07-29 across all five reference implementations (seven
writer classes). Nothing in this repository can emit control byte 4
(`bcMessageEvent`) or its multi-sample variant `0x84`. The only code here that
produces such a frame is the corpus generator
`implementations/rust/osf-core/examples/gen_message_event_refs.rs`, which
hand-assembles the bytes instead of going through a writer.

The question exists because OSF-UP4 made `bcMessageEvent` **read**-mandatory
(DECISIONS §26). Read obligation is not write permission: §26 says writers must
never emit it. The guarantee has two parts, and only one of them was ever in
doubt.

- **Static — the control byte is a closed set.** Every writer picks its control
  byte from three values (`bcContinuedData` 5, `bcStartData` 6,
  `bcAbsTimeStampData` 8), optionally OR'd with the multi-sample bit `0x80`. It
  is a literal at each emit site — or, in Delphi, a literal enum member handed
  to a helper — never a value derived from writer input. Three of the five
  implementations *do* define a named `bcMessageEvent` constant (Rust
  `block.rs:362`, C++ `block.h:353`, Delphi `TBlockContent`), but in every case
  it belongs to the reader-side classification enum and no writer source file
  names it; Java and Python define none at all (Java's reader matches the raw
  literal, `internal/BlockReader.java:389`). `0x84` is unreachable for the same
  reason `0x04` is: the multi-sample bit is only ever OR'd onto 5, 6 or 8.
- **Dynamic — the round trip.** New on this branch, and the one place read
  support could plausibly have leaked into write output. Before OSF-UP4 a
  `bcMessageEvent` block was skipped, so a load-and-rewrite dropped the channel
  silently; now it decodes into the existing time-stamped representation, so its
  content reaches the copy paths (`from_manager` / `fromManager` / the Delphi
  merger) and is re-emitted in *some* encoding.

**What the round trip actually emits: `bcAbsTimeStampData`, bit 7 clear, one
block per sample.** A decoded `bcMessageEvent` is indistinguishable from a
time-stamped `string`/`binary` sample by the time a copy path sees it, so it
re-enters the writer through the ordinary variable-length entry point.
Established by test rather than by reading — see "Tests" below.

#### Cleared by test

Load the corpus file, write it back, walk the raw frame headers of the output,
and read the output back:

| Writer | Evidence |
| --- | --- |
| Rust `WriterBuilder` | Round trip of `osf4_message_event_string.osf` through `WriterBuilder::from_manager` emits five `0x08` frames for `Demo.Message` and no block type 4 anywhere; the five samples reload byte-identically. Every builder entry point (equidistant f32/f64, timestamped numeric, **GPS**, string, binary) is also swept in one file and every emitted block type asserted to be 5, 6 or 8. Static backing: `rust/osf-core/src/writer.rs:424-427` defines exactly three control constants, used at `:618`, `:620`, `:646`, `:648`, `:689`, `:783` — the complete set of emit sites; `ControlKind` (whose `MessageEvent` variant lives at `block.rs:362`) is never named in `writer.rs`. |
| Java `BlockWriter` | Round trip through `BlockWriter.fromManager` — same three assertions, same result. Entry-point sweep as above. Static backing: `internal/BlockEncoder.java:50-52` defines `CTRL_CONTINUED`/`CTRL_START`/`CTRL_ABS_TS`, emitted at `:83`, `:108`, `:138`, `:161`, `:195`; both writers build block bytes **only** via `BlockEncoder.*` (`BlockWriter.java:619-686`), so there is no second emit site to audit. |
| Java `StreamingWriter` | Has no `fromManager`; the test drives the copy sample-by-sample from a loaded manager, which is how a streaming re-emit would be written by hand. Same result. Encoder delegation at `StreamingWriter.java:394`, `:409`, `:667`, `:682`, `:707`, `:712`. |
| Python (PyO3) | `osf.save` of the corpus file emits five `0x08` frames for `Demo.Message`, no block type 4, and the samples reload unchanged. The bindings assemble no blocks of their own — `python/src/writer.rs` (392 lines) forwards NumPy slices, `Vec<String>` and `Vec<Vec<u8>>` into the Rust builder and `py_save` (`:374`) calls `write_to_file` / `from_manager` (`:386-389`) — so this is the Rust path re-verified through the real extension module. The OSF-UP3 audit's weakest row (a pass-through *argument*, no test) is now a tested one. |

#### Cleared by construction (reading only — no test added)

The control byte is unreachable here, so a test could never fail. Cited instead:

| Writer | Evidence |
| --- | --- |
| C++ `StreamingWriter` | Six encoders in `cpp/src/blockencode.cpp` are the only code that writes a control byte: `:110` (`0x06`), `:152` (`0x05`), `:202`, `:252`, `:275`, `:305` (all `0x08`), each OR'd with `0x80` only where a multi-sample form exists. `streamingwriter.cpp` reaches the wire exclusively through them (`:462`, `:506`, `:533`, `:565`, `:609`, `:625`, `:666`). `ControlKind::MessageEvent` (`include/osf/block.h:353`) is reader-side and appears in no writer source file. |
| C++ `BlockWriter` | Same six encoders (`blockwriter.cpp:96`, `:99`, `:113`, `:116`, `:186`, `:192`, `:201`, `:624`). Its round-trip path `copyDcData` (`:756`) routes a `VariableChannel` — which is where a decoded `bcMessageEvent` lands — to `addStringSamples` (`:819`) / `addBinarySamples` (`:828`), i.e. into `blockencode.cpp:252`/`:275`, both of which `push_back(0x08)` unconditionally. |
| Delphi `TOSFFile` | The control byte is built by `OSFMakeControlByte(BlockType, MultiValue)` (`delphi/src/OSF.Types.pas:319`) from a `TBlockContent` enum member. That helper has exactly three call sites in the whole writer — `OSF.Filer.pas:623` (`bcStartData`), `:625` (`bcContinuedData`), `:689` (`bcAbsTimeStampData`) — each passing a literal. `bcMessageEvent` appears in the writer only in `BlockTypeToLogString` (`:564`), a log formatter. Round trip: `osftool convert`/`merge` go through `TOSFMerger`, which re-emits every accumulated sample via `WriteTimestampedBlock` (`OSF.Merger.pas:745`) → `bcAbsTimeStampData`; the decoded message-event samples enter that accumulator as ordinary channel samples (`OSF.Data.Manager.pas:642`). |

#### Tests

`implementations/rust/osf-core/tests/writer_message_event_audit_test.rs`
(4 tests),
`implementations/java/osf-java/src/test/java/com/optimeas/osf/WriterMessageEventAuditTest.java`
(4 tests) and
`implementations/python/tests/test_writer_message_event_audit.py`
(2 tests). All three frame walkers are **per-channel width-aware and dialect-aware**
— the corpus pair is OSF4/XML and declares `Demo.Counter` at
`sizeoflengthvalue = 2` but `Demo.Message` at `4`, while writer output is
OSF5/JSON — so a walker assuming a single width or a single metablock dialect
would misparse the very file the guard depends on.

Each suite opens with an **anti-vacuity guard**: the same detector is pointed at
`generated/osf4_message_event_string.osf`, which carries exactly five
control-byte-4 frames, and is required to find all five. The equivalent file is
checked in the same test as a negative control — it holds the same five samples
as `bcAbsTimeStampData`, so a detector that merely answered "everything" fails
there. The round-trip cases then assert content survival as well as control
bytes: output that carried no block type 4 *because the writer dropped the
channel* would otherwise pass for the wrong reason.

Suite totals after the additions: Rust `cargo test` 189 passed (clippy clean
with `-D warnings`), Java `mvn -pl :osf-java test` 265 passed, Python `pytest`
23 passed / 1 skipped. The Python walker reads channel widths out of the
metablock **text** (regex for OSF4/XML, `json` for OSF5) rather than through the
library, on purpose: a byte-level detector should not depend on the library
agreeing with itself.

#### What remains unknown

- **C++ and Delphi have no executable evidence for the round trip.** Both are
  cleared by reading at the same confidence as the corresponding rows of the
  OSF-UP3 audit. In particular no Delphi test pushes a `bcMessageEvent` file
  through `osftool convert`, so the merger's re-emit is a reading of
  `OSF.Merger.pas`, not a measurement.
- **`datatype=binary` over `bcMessageEvent` has no corpus file.** §26 admits it,
  but the committed pair covers `string` only. The Rust suite compensates with a
  built-not-loaded binary round trip (including payload bytes that are literally
  `0x04`/`0x84`, to prove data is never mistaken for a control byte); Java, C++
  and Delphi have no equivalent.
- **The Python evidence was produced against a locally built extension**
  (`.venv` + `maturin develop`). CI does run `pytest` — in the `build-wheels`
  job, against a freshly built wheel — so the case is covered there too, but it
  runs only on the wheel-building legs, not as a standalone unit job.
- **This audit covers writers in *this repository* only.** The firmware that
  produces the field encoding is outside it — and per §26 it is *conforming* in
  OSF4, so unlike the zero-length-block hunt there is no unidentified defective
  writer to find here.

## Field samples — real recordings

Real data from optiMEAS devices. They cover what synthetic files cannot:
large channel counts, real timestamp patterns, and abrupt stream
endings. Readers are expected to read them without crashing and return
whatever data is present.

| Path | Format | Description |
|---|---|---|
| `motorbike.osf` | OSF4 | 81 channels of motorbike telemetry — speeds, temperatures, GPS, system status |
| `steam_loco.osf` (+ `.csv`) | OSF4 | 123 channels from a steam-locomotive recording (`.csv` is a reference export of the same data) |
| `weather_station.osfz` | OSF4, gzip | 28 channels, gzip-compressed OSFZ — exercises transparent decompression on read |
| `Testdata Motorbike/` | OSFZ | Multi-day motorbike recordings in daily subdirectories (`YYYYMMDD/YYYYMMDD_HHMMSS.osfz`) — robustness/bulk read testing |
